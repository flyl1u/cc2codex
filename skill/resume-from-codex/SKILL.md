# resume-from-codex：接手 Codex 的半成品

用户之前在 Codex 里开发，中途被打断了，可能不止一个会话。你要做的是**接着做下去**，而不是重新设计。

下文的 `codex2cc` 指：

```bash
{{CLI}}
```

## 第一步：确定要接哪些会话

**用户已经点名了某个会话**（比如「接着 Codex 的会话 01a1c928 继续」）：直接跳到第二步，用这个 id。

否则，先看有哪些中断的会话：

```bash
{{CLI}} --interrupted -a --json
```

它只读本地文件，不到一秒。根据 `interrupted` 列表：

- **0 个**：就接当前项目最近的那个会话，第二步不加 `-s`。
- **1 个**：接它。如果它的 `project` 不是当前目录，告诉用户，并在那个目录里工作（桌面版可以先把会话切到那个目录）。
- **多个**：先把列表告诉用户（短 id、标题、项目、中断原因），问一次：「当前会话接 X，其余 N 个各开一个新会话，可以吗？」X 优先选 `project` 等于当前目录的那个。用户同意后：
  - **你能开新会话时**（例如 Claude 桌面版有开启新会话的工具）：为其余每个会话各开一个，工作目录设为它的 `project`，任务写成：
    > 使用 resume-from-codex skill，接手 Codex 会话 `<shortId>`（`<title>`）：运行 `{{CLI}} -s <shortId> -q` 得到交接文档路径，再按 skill 的第二、三步继续。
  - **不能开新会话时**（比如在终端里运行的 Claude Code）：给用户每个会话一行命令，让他们各开一个终端运行：
    ```bash
    cd "<project>" && claude "接着 Codex 的会话 <shortId> 继续"
    ```
  - 然后在当前会话里接 X。

`running` 列表里的会话最近几分钟还在写入，可能仍在运行，不要去接，告诉用户即可。

## 第二步：生成并阅读交接文档

```bash
{{CLI}} -s <shortId> -q
```

（没有指定会话时去掉 `-s <shortId>`。）它会打印交接文档的路径，形如 `<项目>/.handoff/codex-<id 前 8 位>/HANDOFF.md`。每个会话一个目录，多个会话同时接手也不会互相覆盖。每次都重新生成，不要沿用旧文件。

用 Read 完整读这份 `HANDOFF.md`，重点看：

- **用户的全部诉求**：用户原话，是需求唯一可靠的来源，后面的消息会修正前面的。「（回答 Codex 的提问…）」是用户对 Codex 提问的回答，同样算用户的决定。
- **中断状态 / 当前任务列表**：做到哪一步了，还剩什么。
- **中断前最后的现场**：Codex 最后在做什么、跑了什么命令、拿到什么结果。中断在某个工具调用上时，那一步很可能没做完。
- **Git 现状**：会话可能改了项目目录以外的仓库，文档里会一并列出。

需要更多细节时，用 Grep 在同目录下的 `transcript.md` 里搜，不要整篇读完。

找不到会话时：用 `{{CLI}} --list -a` 列出所有项目的 Codex 会话，再问用户要接哪个。

## 第三步：核对，再复述

1. 跑 `git status`、`git diff`、`git log --oneline -10`，确认记录里说的改动确实在代码里。**记录和代码不一致时以代码为准**，并把差异告诉用户。
2. 用三到五句话向用户复述：任务目标、已经完成了什么（提到关键提交或文件）、中断在哪里、你准备的下一步。
3. **等用户确认后再改代码**。用户已经明确说「直接继续」时可以跳过等待。

## 注意

- 多个会话改的是同一个仓库时，提醒用户它们可能互相冲突，建议各自用独立分支或 worktree。
- 沿用 Codex 已经定下的方案、命名和代码风格，除非用户要求改，不要推翻重来。Codex 常用 `codex/` 开头的分支，留意当前在哪个分支上。
- 交接文档里「Codex 说过的话」是上一位助手的说法，不一定正确；用户原话和代码才是事实。
- 记录里提到的推送、部署、发消息等对外操作，即使 Codex 当时准备做，也要先问用户。
- `.handoff/` 目录自带 `.gitignore`，不要提交它。
