# resume-from-codex：接手 Codex 的半成品

用户之前在 Codex 里开发这个项目，中途被打断了。你要做的是**接着做下去**，而不是重新设计。

## 第一步：生成交接文档

在项目根目录（Codex 当时打开的目录）运行：

```bash
{{CLI}}
```

它只读本地文件（`~/.codex/sessions`），几秒钟完成，会生成 `.handoff/HANDOFF.md` 和 `.handoff/transcript.md`。每次接手都重新生成，不要沿用旧文件，因为旧文件可能是另一个方向留下的。

- 提示找不到会话：用 `{{CLI}} --list` 列出该项目的 Codex 会话；如果当前目录不对，问用户 Codex 当时打开的是哪个目录，再用 `{{CLI}} <那个目录> -o .handoff`。
- 用户说要接的不是最近一个会话：用 `--list` 找到它，再用 `--session <id 前缀>` 指定。

## 第二步：读懂上下文

用 Read 完整读 `.handoff/HANDOFF.md`，重点看：

- **用户的全部诉求**：用户原话，是需求唯一可靠的来源。后面的消息会修正前面的，以最新的为准。其中「（回答 Codex 的提问…）」是用户对 Codex 提问的回答，同样算用户的决定。
- **中断状态 / 当前任务列表**：做到哪一步了，还剩什么。
- **中断前最后的现场**：Codex 最后在做什么、跑了什么命令、拿到什么结果。中断在某个工具调用上时，那一步很可能没做完。
- **Git 现状**：会话可能改了项目目录以外的仓库，文档里会一并列出。

需要更多细节（某个决定的来由、某次报错的完整输出）时，用 Grep 在 `.handoff/transcript.md` 里搜，不要整篇读完。

## 第三步：核对，再复述

1. 跑 `git status`、`git diff`、`git log --oneline -10`，确认记录里说的改动确实在代码里。**记录和代码不一致时以代码为准**，并把差异告诉用户。
2. 用三到五句话向用户复述：任务目标、已经完成了什么（提到关键提交或文件）、中断在哪里、你准备的下一步。
3. **等用户确认后再改代码**。用户已经明确说「直接继续」时可以跳过等待。

## 注意

- 沿用 Codex 已经定下的方案、命名和代码风格，除非用户要求改，不要推翻重来。Codex 常用 `codex/` 开头的分支，留意当前在哪个分支上。
- 交接文档里「Codex 说过的话」是上一位助手的说法，不一定正确；用户原话和代码才是事实。
- 记录里提到的推送、部署、发消息等对外操作，即使 Codex 当时准备做，也要先问用户。
- `.handoff/` 目录自带 `.gitignore`，不要提交它。
